# 5. Event Context

This game is part of **Impulse26**, an internal event that promotes:

- UX awareness
- Customer-first mindset
- User research
- UX design techniques
- Human-AI interaction
- AI Agent / Joule thinking
- API and developer experience
- SAP product and platform context
- HPOM collaboration
- Cross-functional product quality

The test should not feel like a formal assessment.  
It should feel like a shareable workplace meme that quietly teaches important product and experience concepts.

---

# 6. Awareness Goals

The game should help employees realize that UX is broader than visual design.

| Awareness Area | Message to Promote |
|---|---|
| **User Research** | Customer comments are not final answers. They are signals that need interpretation. |
| **UX Design Techniques** | Journey maps, prototypes, usability testing, accessibility, information hierarchy, and content design are practical product tools. |
| **Human-AI Interaction** | AI experiences need trust, explainability, control, override, feedback, and fallback. |
| **AI Agent / Joule** | Agentic experiences should reduce user effort and connect tasks, roles, data, and systems. |
| **API Experience** | Developers are users too. API naming, documentation, errors, and contracts are part of UX. |
| **Customer First** | Customer pain needs to enter product decisions, not just remain in workshop notes. |
| **HPOM** | PM, UX, and Engineering need early alignment around customer value, scope, feasibility, and decision ownership. |
| **SAP Context** | Joule, Fiori, BTP, Clean Core, OData, CAP, ABAP, S/4, and enterprise governance can all become playful but meaningful content anchors. |

# 7. Tone and Humor Style

The tone should be:

- Light
- Smart
- Slightly dark
- Workplace-realistic
- Chinese internet-friendly
- SAP-flavored but not official-looking
- Safe for internal sharing
- Funny without attacking any role

## Recommended Humor Style

| Good | Avoid |
|---|---|
| Light black humor | Personal attack |
| Self-roasting workplace jokes | Role shaming |
| SAP/UX/AI/product inside jokes | Confidential product references |
| “This is painfully true” feeling | HR assessment tone |
| Teams / WeChat shareability | Too childish or too formal |

# 9. Four Internal Dimensions

## Dimension A: Signal vs Solution

| Side | Meaning |
|---|---|
| **Signal** | Focuses first on user signals, research insights, experience problems, customer pain |
| **Solution** | Focuses first on system solutions, technical structure, business logic, feasibility |

This dimension helps promote user research awareness without making it sound like “designers vs engineers.”

---

## Dimension B: Human vs Machine

| Side | Meaning |
|---|---|
| **Human** | Focuses on user understanding, trust, control, emotions, adoption |
| **Machine** | Focuses on data, API, AI agent, process, system rules, automation logic |

This dimension connects naturally to Human-AI interaction and API experience.

---

## Dimension C: Explore vs Align

| Side | Meaning |
|---|---|
| **Explore** | Prefers research, prototypes, experiments, quick discovery, divergent thinking |
| **Align** | Prefers HPOM alignment, decision records, scope, owner, feasibility, structured collaboration |

This dimension supports HPOM awareness.

---

## Dimension D: Spark vs Stabilize

| Side | Meaning |
|---|---|
| **Spark** | Pushes ideas forward, creates demos, triggers change, tests fast |
| **Stabilize** | Protects quality, governance, accessibility, Clean Core, production reliability |

This dimension connects to the word “Impulse”: some people spark change; others stabilize it.

# 15. Question Design Principles

The questions should be:

- Scenario-based
- Workplace-realistic
- Short enough for mobile
- Funny but still meaningful
- Not too formal
- Not obviously tied to one “correct” answer
- Balanced across UX, AI, API, HPOM, and product quality

Avoid asking directly:

```text
Are you customer-first?
Are you a UX person?
Do you care about AI governance?
```

Instead, ask:

```text
A customer says, “This part is not very convenient.”
What do you do first?
```

# 16. Sample Question Bank

## 16.1 User Research / VOC

### Q1

A customer says, “This part is not very convenient.” What do you do first?

- **A:** Ask follow-up questions to understand the real workflow pain.
- **B:** Check whether the current behavior matches the designed process.

Dark humor option flavor:

- **A:** “Tell me more.” Then pain-point archaeology begins.
- **B:** “Let me check the process.” Then you discover this is not a bug, but ancestral design.

---

### Q2

A workshop produces ten customer quotes and zero decisions.

- **A:** Cluster the quotes into pain points, roles, and scenarios.
- **B:** Map them to product scope, owners, and feasibility.

Dark humor:

- **A:** Quotes are not insights until someone suffers through synthesis.
- **B:** Without owners, insights become decoration.

---

## 16.2 UX Design Techniques

### Q3

The team has argued about one flow for 30 minutes.

- **A:** Make a quick prototype so people can react to something real.
- **B:** Define decision criteria before the discussion becomes group therapy.

---

### Q4

A screen looks “almost fine,” but something feels wrong.

- **A:** Check hierarchy, spacing, wording, and visual priority.
- **B:** Check whether the screen matches process logic and data states.

Dark humor:

- **A:** It is only 2px, but so is the beginning of chaos.
- **B:** The layout is fine. The underlying process is screaming.

---

## 16.3 Human-AI Interaction

### Q5

The AI agent gives a recommendation confidently.

- **A:** Ask whether users can understand, trust, and override it.
- **B:** Ask what data, permission, and workflow triggered the recommendation.

Dark humor:

- **A:** AI is confident. Users may still have trust issues.
- **B:** The more realistic AI sounds, the more you want to check where it learned that.

---

### Q6

A proposal says, “Let the AI automatically handle this.”

- **A:** Ask where users stay in control.
- **B:** Ask what system boundary, permission, and audit trail are needed.

Dark humor:

- **A:** AI can help. It does not need to become everyone’s new manager.
- **B:** The agent can run, but not naked.

---

## 16.4 API / Developer Experience

### Q7

The API technically works, but the error message is unclear.

- **A:** Improve the message because developers are also users.
- **B:** Check the contract, status code, and documentation consistency.

Dark humor:

- **A:** Developer is also a user, just with better screenshots.
- **B:** 400 Bad Request is not an error message. It is an emotional state.

---

### Q8

A developer asks why an endpoint behaves differently from the documentation.

- **A:** Treat it as an experience gap.
- **B:** Treat it as a contract and governance issue.

Dark humor:

- **A:** Documentation drift is where developer trust goes to die.
- **B:** The API did not lie. It simply developed a second personality.

## 16.5 HPOM

### Q9

PM, UX, and Engineering each have a different understanding of the same feature.

- **A:** Run a quick alignment session around customer value and user flow.
- **B:** Define scope, owner, decision log, dependency, and feasibility risks.

Dark humor:

- **A:** Early alignment is boring, but rework is dramatic.
- **B:** No decision log means everyone gets their own version of history.

---

### Q10

A feature has started implementation, but the user value is still vague.

- **A:** Pause and clarify the customer problem before building more.
- **B:** Identify what can still be adjusted without destroying the sprint.

Dark humor:

- **A:** Building fast in the wrong direction is still fast.
- **B:** The sprint is already moving. Please do not stand in front of it without a plan.

- **B:** Check whether it could become a production incident.

Dark humor:

- **B:** Small bugs grow up fast in production.

The final internal result can be calculated as a 4-letter pattern.

```text
Signal + Human + Explore + Spark
```

```text

JOULE
API
TRIO
```

- Use a tie-breaker question for each dimension.
